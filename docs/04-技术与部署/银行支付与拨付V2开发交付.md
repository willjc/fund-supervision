# 银行支付与拨付 V2 开发交付

## 状态与边界

本分支实现支付补查、本地幂等确认、待拨付生成、资金来源隔离、预占/扣账/冲正、逐笔状态和人工查询重试。复用 BankGateway、MyBatis、Spring 事务和现有 Quartz，不新增中间件。

**尚未完成真实银行接通。** 测试网关仍为 `obk.lovingfox.cn:7000`。IP 放行只是网络条件，不等于接口验收。经用户批准的线上迁移与部署记录见末节；部署成功不代表银行联调通过。

### 必须由银行补齐的协议

- 支付通知 G012002203 的原始 HTTP 样例、验签/解密范围、签名算法、成功应答和重试规则。
- 监管 v1.3 的真实请求封装、网关路由、签名规范版本；`ylzjhb/ylhzqy/ylyeqy` 的受理/最终成功/最终失败/处理中/查无此单码表。
- `ylthtz` 的通知签名封装与传输应答；业务字段 `paylno/retntm/retnrn` 已明确。

因此郑州银行的 `supportsPayout()` 固定为 false，监管提交/查询/余额方法保护性拒绝；本地已实现文档业务字段校验、载荷构造和可控模拟网关，但没有猜造可运行的 HTTP 协议。支付与退汇通知入口固定 HTTP 503，不解析、不记账、不伪造 ACK。**仅修改开关不能解除这些协议保护。** 收到银行材料后仍需补实现并验证适配器。

## 已实现流程

- 未支付订单的最近支付尝试明确 FAILED 后，正常支付入口创建新请求号并递增 attempt_no，保留旧流水；PENDING/UNKNOWN 复用原请求，SUCCESS 不重复发送。订单行锁串行化并发点击，并重新校验订单状态、机构、金额和已收金额。
- 页面查单和后台补查统一进入 `BankPaymentReconciler`，保存银行流水/时间/结果后调用既有入账事务；成功后的本地重试不再次查单或发送资金。
- 首月不再提前扣账，创建 pending 拨付；线下入住/线下支付同样不伪造首月银行完成，但不获得真实拨付资格。
- 首月/月度按原银行订单核验来源；人工申请仍保留家属/监管审批，审批只关联待拨付单；押金审批生成独立待拨付单。
- 只有新确认的银行资金增加 `bank_service_balance/bank_deposit_balance`，旧余额、现金、mock 不回填资格。数据库预占必须同时满足账面可用余额和新银行来源余额。
- 银行提交前落库请求号、账户快照和预占。查询必须匹配请求号；成功还必须具备银行流水、时间、精确金额及收付款账户。受理不等于成功。
- 明确失败释放预占；原交易未知不得重新发送。授权重试创建新 attempt/requestNo，同业务最多一笔未决记录。
- 退汇冲正保留原始交易和流水；先于查询到达时只释放预占，已扣账时只返还一次。已确认事实与本地记账失败分开保存，可重入恢复。
- 通用新增不能授予 bankEligible；银行拨付及关联申请禁止通用编辑/删除。查询/重试受现有权限和机构范围约束。
- 监管账户户名按银行准确登记，不再由机构名称拼接。有银行余额/未决交易时禁止更换账户；已有商户配置不能移动至其他机构。
- 普通拨付页面改为真实数据，保留申请/家属流程；审批与到账分开展示，账面/预占/可用/银行余额分别标识，历史完成不冒充银行到账。

## 接口与任务

| 接口 | 当前行为 |
|---|---|
| `POST /h5/payment/process/{orderId}` | 发起/继续支付；明确失败后新建尝试，未决不重复发送 |
| `GET /h5/payment/status/{orderId}` | 用户权限检查后查单、确认入账 |
| `POST /bank/zzbank/notify/payment` | 协议待确认，503 |
| `POST /bank/zzbank/notify/returned` | 协议待确认，503 |
| `POST /pension/bank/payout/{transferId}/query` | 查询银行结果并补本地记账，不返回账户快照 |
| `POST /pension/bank/payout/{transferId}/retry` | 仅已确认失败且本地释放完成可新建尝试 |
| `GET /pension/bank/payout/balance/{institutionId}` | 返回银行可用余额及查询时间；当前真实协议未开放 |

银行回调公网地址为 `https://mz.dayushaiwang.com/api/bank/zzbank/notify/payment`。已为 `/api/bank/zzbank/notify/` 增加窄范围转发，管理端 `/prod-api` 和 H5 原 `/api` 路由不变。POST 实测返回保护性 503；当前不要配置 `ZZBANK_CALLBACK_URL` 指向该入口，协议适配验收后再填写。

`bankSettlementTask.reconcile()` 每 15 秒扫描持久化到期查询；支付满 60 秒首次查询，覆盖至 150 秒，之后每 5 分钟，24 小时未明确转人工，不标失败。已知银行成功/失败/退汇的本地恢复不按未知交易超时结束。

`bankSettlementTask.dispatch()` 每分钟扫描到期拨付，按 ID 游标分页；阻塞记录不挡住后续记录。月度按配置日/时间判断已到期，月底不足指定日取当月最后一天，支持重启补执行。旧任务入口不再直接记账。

`ZZBANK_PAYOUT_ENABLED`、`ZZBANK_RECONCILIATION_ENABLED` 默认 false；新 Quartz 任务默认暂停。禁用新发送后仍可人工查询已受理交易。

## 数据迁移、备份、回滚

迁移文件：`sql/zzbank_payment_payout_v2.sql`，基于已检查的 MySQL 8 表结构。先应用 V1 表结构；V2 只执行一次，DDL 隐式提交，不能靠事务整体回滚。新增字段、索引、任务定义，并将旧 SUCCESS 标记为本地已记账；不改历史余额，不为历史拨付授予资格。

线上实施需单独批准（本次已获批准，执行记录见末节）：

1. 停止新银行请求并暂停相关任务，核对所有在途交易；保存当前应用包、启动脚本、配置、任务定义。
2. 使用安全凭据方式备份 `bank_transaction/bank_merchant_config/account_info/fund_transfer/fund_transfer_apply/fund_transfer_apply_detail/deposit_apply/payment_record/expense_record/supervision_account_log/order_info/sys_job` 的结构和数据；不要把密码写入命令或交付文档。确认备份非空并在隔离库试恢复。
3. 核对 SHOW CREATE TABLE、索引和迁移适用性，逐条执行 SQL，再核对历史笔数、分类余额合计、旧拨付资格仍全为 0、任务仍暂停、新金额字段精度。
4. 部署兼容 V2 的应用，先只验收查询和本地恢复；逐机构确认签约、商户和账户后，另行启用发送。

回滚优先关闭新发送、保留补查和新增审计字段。**银行已经发生交易后，不恢复旧库、不 DROP 新字段、不运行旧假拨付逻辑。** 无 V2 交易时也需审批才能恢复备份；已有资金移动须按银行事实向前修复。

现有 47 笔历史待拨付以及旧 PENDING 支付不自动纳入新发送。需要业务与银行核实后另行制定转换操作，不能批量设置资格。

# 拨付全流程（郑州银行监管账户）

本文按实际操作顺序说明养老机构预收费资金从“账户登记”到“银行拨付完成、对账、退汇”的完整流程，并对照当前代码说明哪些环节已经实现、哪些仍需人工或银行条件。管理端入口：**拨付流程**（`/payout`，流程总览 + 拨付单据）。

> 口径说明：
> - “开户”指银行侧实际开立监管专户和基本账户，必须在银行完成；平台做的是登记账户、绑定商户、发起签约，不能代替银行开户。
> - 702 受理成功不等于拨付成功，最终状态以 703 查询结果和银行流水为准。
> - 历史本地“已完成”记录没有银行交易凭证，只作历史展示，不会自动补发。

## 一、角色与前置条件

| 角色 | 职责 |
| --- | --- |
| 养老机构 / 财务 | 提供真实的监管专户、基本账户、户名、开户行和联行号；发起月度拨付申请（如需） |
| 民政监管 / 平台管理员 | 审核机构账户资料；配置银行商户；审批拨付单；核对银行流水 |
| 银行 | 开立账户、提供测试/生产商户号、完成 701 签约、受理 702、返回 703/707/708/709 结果 |
| 运维 | 配置银行网关地址、密钥、`BANK_INTEGRATION_MODE`、拨付总开关和协议验收标记 |

前置条件（缺一不可）：

1. 银行已实际开立监管专户和基本账户。
2. 平台已登记两户的账号、户名、开户行；监管户名与基本户名必须完全一致。
3. 银行已分配商户号（merId），并完成测试环境验证。
4. 银行已完成 701 监管协议签约并返回签约编号（jgxyno）。
5. 平台侧拨付总开关打开、协议验收标记为 true、机构商户拨付开关打开。

## 二、全流程（10 个环节）

### 01 开立并登记监管账户与基本账户

- 操作页面：监管账户管理 → 账户管理（`/supervision/account/institutionAccount`）。
- 登记内容：
  - 监管专户：`superviseAccount`（账号）、`superviseBank`（开户行）、监管户名。
  - 基本账户：`bankAccount`（账号）、`basicBank`（开户行）、基本户户名。
- 平台校验：
  - 两账户信息不完整时，不能进入商户绑定和签约。
  - 已存在银行资金或未决银行交易时，禁止修改账户信息，避免旧账户继续收发资金。
- 修改账户的联动：机构账户/开户行变更会使原商户配置的验证状态、签约编号、启用状态和拨付开关失效，必须重新验证、重新 701 签约。

### 02 绑定银行商户号

- 操作页面：监管账户管理 → 银行商户配置（`/supervision/account/supervisionAccount`）。
- 登记内容：merId、商户名称、渠道类型、环境（测试/生产）、是否默认、是否跨行、基本户联行号。
- 平台自动带出：监管账号/户名、基本账号/户名来自机构账户档案，不允许在商户配置里另造一套账户。
- 校验：
  - 同一银行环境下 merId 不可重复绑定。
  - 新建配置默认 `verify_status=0`、`status=0`、`payout_enabled=0`，不会自动具备拨付资格。
  - 设为默认绑定时，同一机构其他配置取消默认。
- 保存后系统自动调用银行商户验证；验证失败会记录银行返回说明，不能启用。

### 03 银行环境验证

- 触发方式：保存商户配置后自动验证，也可在列表手动“验证”。
- 银行交互：使用商户号和监管账号向银行查询，测试网关返回“已接受该商户号”视为验证通过。
- 结果：
  - `verify_status=1`：验证通过，可启用配置。
  - `verify_status=2`：验证失败，页面展示 `verify_message`，修正后重新验证。
- 只有验证通过的配置才能把 `status` 置为启用。

### 04 监管协议签约（701 / ylcntr）

- 操作：商户配置列表点“签约”。
- 前置校验：
  - 监管户名必须与基本户户名完全一致（银行规则，本地先拦截）。
  - 基本账户、基本户名、跨行联行号必须完整。
  - 已有签约编号的绑定不能重复签约。
- 银行交互：调用 `OBK0071701`，成功必须返回协议编号 `jgxyno`；只受理但无协议号视为未完成，需人工核查。
- 结果：协议编号写回 `bank_merchant_config.supervision_agreement_no`，作为开启机构拨付开关和发送 702 的必要条件。

### 05 开启拨付闸门

拨付发送同时受四道闸门控制，全部满足才允许发送：

| 闸门 | 配置位置 | 说明 |
| --- | --- | --- |
| 平台拨付总开关 | 后端 `bank.integration.payout-enabled` / `ZZBANK_PAYOUT_ENABLED` | 关闭时所有真实拨付拒绝 |
| 银行监管协议验收 | `bank.integration.payout-protocol-confirmed` / `ZZBANK_PAYOUT_PROTOCOL_CONFIRMED` | 未验收时网关 `supportsPayout()` 为 false |
| 商户验证与启用 | `bank_merchant_config.verify_status=1`、`status=1`、`is_default=1` | 必须使用当前默认绑定 |
| 机构拨付开关 | `bank_merchant_config.payout_enabled=1` | 同时要求签约编号存在、账户户名完整 |

“拨付流程”页会实时显示四道闸门是否就绪；后端在发送时仍会再次校验，页面状态不能替代服务端校验。

### 06 收单入账（形成可拨付来源）

- 老人在 H5 收银台通过郑州银行支付成功后，后端完成订单支付、账户余额和监管流水更新。
- 仅“郑州银行真实支付成功”的订单会：
  - 增加账户的银行来源余额（`bank_service_balance` / `bank_deposit_balance`）；
  - 调用 `qualifyOrder` 把该订单已生成的待拨付单置为 `bank_eligible=1`。
- 历史本地完成、现金或模拟支付记录不会形成可拨付额度，也不会被补发。
- 支付成功后自动生成：
  - 首月拨付单：`source_key=FIRST:{orderId}`，立即到期；
  - 后续月份拨付单：`source_key=MONTH:{orderId}:{yyyy-MM}`，按划拨规则日期到期。

### 07 生成拨付单

- 拨付单是“一个老人 + 一个资金类别（服务费/押金）+ 一个来源”的最小执行单元。
- 关键字段：
  - `bank_eligible=1` 才具备银行拨付资格；
  - `source_key` 必须能对应到已成功的银行支付或已审批押金申请；
  - `transfer_date` 是应拨付日期；
  - `status`：`pending` → `processing` → `completed` / `failed` / `returned` / `cancelled`。
- 旧数据或 `bank_eligible≠1` 的单据只读展示，不能审批、发送或补发。

### 08 审批拨付单

- 操作：拨付单据 → 审批，填写通过/拒绝和审批意见。
- 审批前置：`bank_eligible=1`、`status=pending`、`is_paid=0`、尚未绑定银行交易。
- 审批结果：
  - 通过：写入审批人和审批时间，仍为 `pending`，等待发送；审批本身不扣款、不调银行。
  - 拒绝：状态置为 `cancelled`。
- 手动拨付申请（`fund_transfer_apply`）会把申请明细关联到拨付单，并置为手动拨付、当日到期。

### 09 发送与查单（702 / ylzjhb + 703 / ylhzqy）

发送前：

1. 服务端校验拨付闸门、商户签约、账户来源、单据资格。
2. 对月度自动拨付校验到期日：未到 `transfer_date` 不能手动提前发送；手动申请和失败重试除外。
3. 调用 709 查询监管账户可用余额，余额不足或无法确认时保留待拨付，不发送。
4. 在本地事务中锁定机构、商户和拨付单，校验来源支付，预占账户余额，插入 `bank_transaction`（请求号 `BT...`），绑定拨付单。

发送与记账：

1. 事务提交后调用 702 向银行发送；付款方为监管专户，收款方为基本账户。
2. 立即用原请求号调用 703 查询最终状态。
3. 按银行结果记账：
   - `SUCCESS`：扣减预占和账户余额，写费用流水与监管流水，拨付单 `completed`，记录银行流水号。
   - `FAILED`：释放预占，拨付单 `failed`，允许在满足条件时新建请求重试。
   - `RETURNED` 或 707 退汇：冲正预占/余额，写收入流水，拨付单 `returned`。
4. 若 702 通信异常、超时或结果未知：只保留原请求并查询原单，**不得重新发送**；后台对账任务会继续查单。

幂等与并发：

- 一笔拨付单同一时间只允许一个有效银行请求；已有请求时只能查询或满足条件后重试。
- `attach`、余额预占、记账更新都带条件，重复请求不会二次扣款。
- 退汇通知必须来自经验证的银行通道，不能直接把 HTTP 参数当通知内容。

### 10 对账与退汇（708 / ylmxqy、709 / ylyeqy、707）

- 708：按日期查询监管账户银行交易明细，核对每笔 702 的实际扣账、金额、对方账户和银行流水号。
- 709：查询监管账户可用余额，与平台银行来源余额、预占和未决交易交叉核对。
- 707：银行退汇通知进入后，系统记录退汇时间/原因，触发原请求查单并冲正。
- 对账差异处理页面用于人工核对平台流水与银行流水差异；未决交易不能直接改状态，必须先查银行。
- 对账是持续动作，不以平台内部余额代替银行结果。

## 三、状态机

`fund_transfer.status`：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `pending` | 待审批或已审批待发送 | 审批；已审批且到期可发送 |
| `processing` | 已有银行请求，等待最终结果 | 只能查询原请求 |
| `completed` | 银行明确成功且本地已记账 | 查询、对账 |
| `failed` | 银行明确失败且本地已释放预占 | 查询；满足条件可失败重试 |
| `returned` | 银行退汇且本地已冲正 | 查询、对账 |
| `cancelled` | 审批拒绝 | 只读 |

`bank_transaction.status / booking_status`：

| 场景 | status | booking_status | 说明 |
| --- | --- | --- | --- |
| 已发送待查 | `PENDING` / `UNKNOWN` | 空 | 只能查原单 |
| 成功已记账 | `SUCCESS` | `DONE` | 已扣账 |
| 失败已释放 | `FAILED` | `DONE` | 可判断是否重试 |
| 退汇已冲正 | `RETURNED` | `REVERSED` | 资金已退回 |
| 退汇待冲正 | `RETURNED` | `RETURN_PENDING` | 等待对账任务处理 |
| 人工核查 | 原状态 | 原状态 | `manual_review=1`，停止自动查询 |

## 四、异常处理矩阵

| 异常 | 处理原则 | 禁止动作 |
| --- | --- | --- |
| 709 余额不足/查询失败 | 保留待拨付，稍后重试 | 跳过余额校验直接发送 |
| 702 超时/网络异常 | 用原请求号查 703，后台继续对账 | 新建请求重复发送 |
| 703 返回处理中/未知 | 保持 `processing`，按计划继续查单 | 人工改成成功/失败 |
| 银行明确失败 | 释放预占，拨付单 `failed`，满足条件可重试 | 对处理中单据重试 |
| 银行成功但字段不匹配 | 停止记账，标记人工核查 | 按本地推测扣账 |
| 退汇 | 冲正预占和余额，回写 `returned` | 再次发送同一拨付单 |
| 账户/绑定变更 | 先核对银行资金和未决交易，再变更并重新验证签约 | 变更后沿用旧签约编号 |

## 五、当前实现对照与本次优化

### 已修正/已实现

1. **流程不可见**：新增“拨付流程”总览页，把账户、商户、验证、701 签约、闸门、收单、生成、审批、发送、对账串成 10 个步骤，并实时显示待办数量。
2. **提前发送漏洞**：月度自动拨付单未到 `transfer_date` 时，后端拒绝手动发送；前端不再显示“立即发送”，改为“未到拨付日”。手动申请和失败重试不受此限制。
3. **闸门不透明**：流程页集中展示平台开关、协议验收、商户验证/启用、机构拨付开关；发送时后端仍逐项校验。
4. **历史与新拨付混用**：列表用“历史记录（未接入银行）”标注 `bank_eligible≠1` 的已完成记录，流程页单独统计 `legacyCompleted`，历史记录不参与审批和发送。
5. **流程与单据混杂**：页面拆为“流程总览”和“拨付单据”两个视图，流程页回答“现在该做什么”，单据页执行审批/发送/查单。
6. **账户变更风险**：机构账户或开户行变更会使商户验证、签约、启用和拨付开关失效；存在银行资金或未决交易时禁止变更。
7. **重复发送风险**：已有银行请求只能查询；仅银行明确失败、本地已记账且拨付单为 `failed` 时才允许新建重试。
8. **退汇一致性**：707/703 确认退汇后自动冲正预占和账户余额，并回写拨付单和申请汇总。
9. **详情越权读取**：拨付单详情接口增加机构数据范围校验，非本机构用户不能通过单据 ID 读取其他机构拨付详情。

### 仍需人工或银行配合

1. 自动发送任务保持暂停，由操作员核对闸门和单据后逐笔发送；是否恢复自动发送需单独评审。
2. 708/709 对账目前以页面人工核对为主，未实现自动差异闭环。
3. 真实 702 仍需银行测试商户、监管协议、密钥和网络条件全部验收后再开闸；当前代码具备能力不等于已完成真实联调。
4. 菜单中“资金划拨管理”（菜单 2170，旧入口）与“拨付流程”指向同一组件，建议后续只保留一个入口，避免操作员从旧入口进入后误以为审批即扣款。

## 六、上线前检查清单

- [ ] 银行已开立监管专户和基本账户，户名完全一致。
- [ ] 机构账户档案两户信息完整，且与银行一致。
- [ ] 商户配置 merId 唯一、验证通过、已启用、设为默认。
- [ ] 701 签约成功并回写协议编号。
- [ ] 平台拨付总开关、协议验收标记、机构拨付开关均已确认。
- [ ] 已用测试单据完成 702 → 703 → 本地记账 → 708/709 对账闭环。
- [ ] 已演练 702 超时只查原单、明确失败重试、退汇冲正三类异常。
- [ ] 自动发送任务仍处于暂停状态，或已完成恢复评审。
